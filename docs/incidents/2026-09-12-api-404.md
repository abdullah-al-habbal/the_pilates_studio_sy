# Incident Report: 2026-09-12 API 404 (Production)

## 1. Summary

Production (`https://pilatesstudiosy.com`) returned HTTP 404 `ENDPOINT_NOT_FOUND`
for `POST /api/v1/public/app-version` and `GET /api/v1/me`, while dev
(`https://dev.pilatesstudiosy.com`) and local returned the expected 200/401
responses. The failure was caused by a stale `bootstrap/cache/routes-v7.php`
route cache on the production server whose content did not include the
registered API v1 routes. Clearing the route cache restored correct behavior.
The mechanism that produced the stale, route-incomplete cache could not be
identified.

## 3. Root cause

Verbatim: "I do not know the root cause."

Ruled out, with the evidence used:

- **OPcache staleness** — measured live: `opcache.enable=On`,
  `validate_timestamps=On`, `revalidate_freq=2`, `file_update_protection=2`.
  Multi-day stale OPcache is inconsistent with these settings.
- **A second Laravel root / duplicate cache paths** — the server hosts exactly
  two artisan roots (production and dev); no other `bootstrap/cache` or artisan
  files found.
- **Conditional route registration** — `routes/api/api.php` and
  `routes/api/v1/v1.php` are unconditional `require` chains; no environment- or
  user-dependent conditionals; route files at cache-write time matched commit
  `078d8fd`.
- **Code drift** — production, dev, and local all pointed at `078d8fd` at the
  incident time; trees were byte-identical.
- **A GitHub Actions deploy** — no Actions run exists for 2026-09-08; the
  deploy that night was manual. Composer autoload files (Jun 8 / Aug 29)
  prove `composer install` did not run on Sep 8.

## 4. Immediate fix

`php artisan route:clear` was executed on production, which removed the stale
`routes-v7.php` and made routes load live again. This was applied **without
prior approval** and was disclosed to the stakeholders immediately after the
fact. It is not byte-restorable; the route cache was not regenerated.

## 5. Deploy hardening

Changes to `.github/workflows/deploy.yml`:

- `route:cache` removed from phase 5 (it was the single point of failure for
  the incident; route loading is live).
- Early `artisan optimize:clear` added after git sync, guarded with
  `|| echo "⚠️ Early clear failed — vendor may be stale, continuing"` so a
  `composer.json` bump cannot abort the deploy before `composer install` runs.
- Environment-aware post-deploy health check on
  `/api/v1/public/app-version` via `$HEALTHCHECK_URL`; deploy fails unless the
  endpoint returns HTTP 200 with `"success":true`.
- `script_stop` input removed — not supported by `appleboy/ssh-action@v1`
  (verified against its `action.yml`); the remote script's
  `set -Eeuo pipefail` plus explicit `exit 1` is the real protection
  (failure path proven).
- `[fresh-migrate]` check now passes the commit message via an `env`
  variable (`HEAD_MSG`) instead of raw shell interpolation, fixing a
  shell-injection failure on messages containing double quotes or
  parentheses.
- `chmod -R 775 storage bootstrap/cache` replaced with
  `find storage bootstrap/cache -type d -exec chmod 775 {} \;` and
  `find storage bootstrap/cache -type f -exec chmod 664 {} \;` so the execute
  bit is never set on tracked files (stopped the per-deploy `100644 → 100755`
  mode churn on the 11 tracked `.gitignore` files).

## 6. Verification

- Post-fix deployments were green (health check, `/me` 401,
  `app-version` 200).
- `/api/v1/me` with an invalid bearer token → 401 UNAUTHORIZED.
- Unknown path → 404 (correct 404 behavior).
- `bootstrap/cache/routes-v7.php` confirmed ABSENT on production.
- `artisan about` on production: Config CACHED, Routes NOT CACHED,
  Views CACHED.
- Production and dev servers' git HEAD match `origin/production` / `origin/dev`.
- `git status --short` empty on both servers after the mode-churn fix.
- **Health-check failure-propagation test:** the dev `HEALTHCHECK_URL` was
  deliberately pointed at a 404 path (`__fail_probe__`); the resulting deploy
  run failed with exit code 1 and `conclusion: failure` after printing
  `❌ HEALTH CHECK FAILED`. The change was then reverted and dev re-deployed
  green.

## 7. Open items

Root cause of the stale route cache remains **unknown**. `config:cache`
could theoretically exhibit analogous behavior but has not; there is no
evidence either way. No further action is planned.
